# kyo-ffi on Scala Native: the NoSuchElementException and the macOS abort

Static analysis only. Nothing here was run; every claim cites a file and line, or a CI log line fetched with
`scripts/ci-logs.sh` from the two runs the review names (34676060392 and 34683181614 on `fwbrasil/kyo-ci-test`).
Scala Native sources are quoted from the 0.5.12 sources jars in the local Coursier cache
(`javalib_native0.5_3-0.5.12-sources.jar`, `nativelib_native0.5_3-0.5.12-sources.jar`); the version is pinned at
`project/plugins.sbt:15`.

## Summary

The premise of the brief is only half of the evidence. In one of the four Native CI failures the failing leaf is
the throwing comparator of `ItCallbackExceptionTest`, where a trace is printed from inside a C callback. In the
other three the failing leaf is `kyo_it_struct_read_handle › struct with opaque field` of `ItStructPtrTest`, which
never invokes its callback and never prints a trace: the C function only dereferences a pointer. Both leaves fail
with a `java.util.NoSuchElementException` that has no message, and both are the first leaf of their suite. A
message-less `NoSuchElementException` cannot come from `EffectTrace`: every partial operation there sits inside a
catch-all, and the one collection that could throw is guarded by a size check. It also cannot come from Scala
Native's DWARF decoder, which is written with `Option` and a bounded binary search. On the Native javalib the
exception with that exact shape is thrown by `java.util.ArrayDeque.removeFirst`, and the one call to it on both
failing leaves is `CallbackRegistry.popTransient_<shape>()` in the generated `finally` of every downcall that
carries a transient callback, including a struct with a function pointer field. Whether that pop is the thrower is
the question a run has to answer, because the transcript that would say so is not printed: kyo-test renders an
unexpected leaf exception as `t.toString` alone. The macOS abort is a separate, fully explained mechanism: the
generated trampoline lets an exception escape into C (the callback lookup sits outside its `try`, and the reporter
inside its `catch` is itself unguarded), the C frames of `qsort` on macOS carry no unwind information the runtime
can step through, so the C++ runtime cannot find a handler and calls `abort`. On Linux the same escape unwinds
through `.eh_frame` and lands in the generated `finally`, which is where a message-less `NoSuchElementException`
would replace whatever escaped.

## 1. The path from a throw inside a C callback to `printStackTrace`

Registration. For a transient callback parameter the Native emitter creates the C function pointer from a top-level
trampoline and pushes the user function onto a per-shape, per-thread stack before the downcall
(`kyo-ffi/codegen/src/main/scala/kyo/ffi/codegen/emitters/NativeEmitter.scala:255-282`, the pop line built at
`:278-280`); the pop is collected as a teardown line and emitted in a `finally` around the call block
(`NativeEmitter.scala:432-449`), while the push and every other setup line are emitted before the `try`
(`NativeEmitter.scala:326-330`). A function pointer field of a struct parameter takes the same route: the struct
writer pushes the field's function during marshalling and adds the pop to the enclosing call's teardown
(`NativeEmitter.scala:517-541` packed, `578-600` non-packed; the collector is created per struct parameter at
`NativeEmitter.scala:216-235`). So the leaf `kyo_it_struct_read_handle(res)`
pushes on `transientStack_I_U` and pops it in `finally` although C never calls the pointer.

The trampoline. The per-shape trampolines are generated by `project/CallbackShapesGen.scala:349-357` into
`kyo-ffi/native/target/scala-3.8.4/src_managed/main/kyo/ffi/internal/CallbackRegistryShapes.scala`. For the sort
comparator (`II_I`) the generated code is (`CallbackRegistryShapes.scala:309-316`):

```scala
def trampolineT_II_I(p0: CInt, p1: CInt): CInt =
    val tagged = peekTransient_II_I()
    try tagged.fn.asInstanceOf[(Int, Int) => Int].apply(p0, p1)
    catch
        case t: Throwable =>
            FfiGenErrors.reportCallbackFailed(tagged.bindingFqn, tagged.methodName, tagged.kind, t)
            0
```

Two things about its shape matter later: `peekTransient_II_I()` runs outside the `try`, and it throws
`IllegalStateException` when the per-thread stack is empty (`mustPeek`, `CallbackRegistryShapes.scala:186-195`,
template at `CallbackShapesGen.scala:262-275`); and the `catch` arm calls the reporter with no guard of its own.

The reporter. `FfiGenErrors.reportCallbackFailed` prints the one-line diagnostic and then
`t.printStackTrace()` (`kyo-ffi/shared/src/main/scala/kyo/ffi/internal/FfiGenErrors.scala:19-22`). The retained
trampolines call the same reporter from inside a `try`/`catch`/`finally` that also brackets the guard's in-flight
counter (`RetainedTrampolines_I_U.scala:11-24`).

The thread and the stack. C invokes the pointer synchronously on the thread that made the downcall
(`kyo_it_sort_ints` sets a static and calls `qsort`, `kyo-ffi/it/shared/src/main/c/kyo_it_callbacks.c:31-34`; the
adaptor at `:22-29` calls the Scala pointer). That thread is a kyo scheduler pool thread, created by
`kyo-scheduler/jvm-native/src/main/scala/kyo/scheduler/util/Threads.scala:21` with `new Thread(null, r, name, 0L,
false)`, because kyo-test runs every leaf body as its own fiber under `Scope.run` and `Fiber.initUnscoped`
(`kyo-test/runner/shared/src/main/scala/kyo/test/runner/TestRunner.scala:462`), the body being a thunk taken
inside `Sync.defer` (`TestRunner.scala:424-425`), under `Async.timeout` (`:444`), inside the evaluator's guarded
loop (`kyo-kernel/shared/src/main/scala/kyo/kernel/internal/Eval.scala:502-513`). From the throw point downward the
physical stack is: the user lambda, `trampolineT_II_I`, `kyo_it_qsort_adaptor`, the libc sort (on macOS the
insertion-sort helper `_isort`), `qsort`, `kyo_it_sort_ints`, the generated `ItCallbacksBindingsImpl.kyoItSortInts`
body inside `Zone.acquire`, the leaf thunk, `Eval.loop`, the IOTask, the scheduler worker, the pool thread.

What `printStackTrace` walks on Scala Native. `java.lang.Throwable.printStackTrace()` goes to `System.err`
(`java/lang/Throwables.scala:98-102`) and the private overload prints `toString`, then every element of
`getStackTrace()`, then the cause chain with duplicate trimming; suppressed exceptions are not printed at all
(`Throwables.scala:109-150`). `getStackTrace()` is lazy: the constructor's `fillInStackTrace` only records raw
instruction pointers by walking the physical stack with libunwind (`scala/scalanative/runtime/Throwable.scala:27-38`
calling `StackTrace.currentRawStackTrace()`, `scala/scalanative/runtime/StackTrace.scala:41-85`, which loops
`unwind.step` until it returns zero or negative, `scala-native/platform/posix/unwind.c:37-43`). The walk starts at
the throw point and continues through the C frames only as far as libunwind can step: a frame without unwind
information ends the walk, which is why the trace observed locally stops at `_isort` after eight frames. The first
`getStackTrace()` materializes those pointers (`runtime/Throwable.scala:67-74`, `StackTrace.materializeStackTrace`
at `StackTrace.scala:86-126`), caching the result in the throwable, so a later `printStackTrace` does no
symbolization of its own. Each pointer is resolved once per thread through `tlContext.cache` and
`makeStackTraceElement` (`StackTrace.scala:194-244`): the executable's own DWARF is consulted first
(`Backtrace.decodePosition`, `scala/scalanative/runtime/Backtrace.scala:32-64`, over the tables parsed once at
module initialization by `processFile`, `:157-206`), and a pointer outside those tables, which is what every C
frame of libc or of `libkyo_it_bundled` is, falls back to `dladdr` (`unwind.c:71-90`) and to
`SymbolFormatter.asyncSafeFromSymbol` (`StackTrace.scala:246-276`). None of that is the `EffectTrace` splice: the
suppressed carrier is never read by `printStackTrace`, and on this path no kyo code runs between the throw and the
print.

## 2. The partial operation

### 2.1 `EffectTrace`, line by line

`kyo-kernel/shared/src/main/scala/kyo/kernel/internal/EffectTrace.scala`:

- `splice` (`:100-116`) runs only for a non-fatal throwable that is not `NoStackTrace`, and its whole body, the
  `find`, the `getStackTrace`, the `filterNot(isPlumbing)` and the `setStackTrace`, sits inside
  `try ... catch case failure if !IsFatal(failure) => ()`. A `NoSuchElementException` raised anywhere in it is
  swallowed. `physical` (`:37`) is a cache of the filtered frames on the carrier, read at `:106-111`; it is a
  `Maybe` matched, never `get`.
- `isPlumbing` (`:118-119`) would throw a `NullPointerException` on a null class name; Scala Native builds every
  class name with `fromCString` (`StackTrace.scala:270-275`), so it is never null, and the throw would be swallowed
  anyway.
- `find` (`:121-130`) is a bounded loop over `getSuppressed`, total.
- `carrierOf` (`:132-141`) allocates the carrier under `ex.synchronized`, total.
- `reconstruct` (`:77-93`) wraps the builder in the same catch-all.
- `Builder.frame` (`:160-172`) skips a null frame and checks `full` before writing `out(size)`.
- `Builder.push` (`:189-198`) calls `work.removeLast()` only when `work.size == maxTraceFrames`, so the deque is
  never empty there; and Scala's `mutable.ArrayDeque.removeLast` on an empty deque throws with the message
  "empty collection", which is not the shape observed.
- `drain` (`:221-268`) tests `work.isEmpty` before `removeHead()`.
- `regions` (`:208-219`) is bounded by `stack.depth`; `Park` (`:250-259`) by `entries.regions`.

Conclusion: `EffectTrace` has no partial operation that can surface. A trace of eight frames ending in a C frame
is filtered by `isPlumbing` (none of the eight starts with `kyo.`) and concatenated; nothing there fails. If
`materializeStackTrace` threw inside `splice`, the exception would be swallowed and the throwable would keep its raw
pointers for the next caller, but that next caller is never the callback reporter, which runs before any kyo code
sees the exception.

### 2.2 Scala Native's decoding

`Backtrace.decodePosition` is `Option`-shaped end to end (`Backtrace.scala:32-64`); `search` is a bounded binary
search (`:66-86`); `dwarfInfo` is computed once by `processFile` (`:25`, `:157-206`) and matched as an `Option`.
`DWARF.parse` looks abbreviations up through `abbrevCache.get` and `idx.get(code).foreach`
(`scala/scalanative/runtime/dwarf/DWARF.scala:228-236`, `:258-261`); its only throws are a `RuntimeException` and
an `Exception("Unsupported form")` (`:306`, `:400`) plus assertions. `SymbolFormatter.scala` throws nothing.
`makeStackTraceElement` handles the `dladdr` failure by an empty symbol buffer (`unwind.c:81-90`,
`StackTrace.scala:219-238`). So a C frame such as `_isort` is decoded as an unknown symbol, never as a missing
element.

### 2.3 What the exception's shape says

kyo-test renders a non-assertion failure as `t.toString` (`TestRunner.scala:523` for `Result.Failure`, `:531` for a
panic) and `ConsoleReporter` prints that diagram (`ConsoleReporter.scala:110-120`); on Native `Throwable.toString`
is the class name alone when the message is null (`Throwables.scala:170-175`). The logs show exactly
`java.util.NoSuchElementException`, so the message is null. That excludes `Maybe.get`
(`kyo-data/shared/src/main/scala/kyo/Maybe.scala:178`, message "Maybe.get"), `Dict` lookups (`Dict.scala:145`, the
key), Scala's `Iterator.empty.next` and `ArrayDeque.removeHead`, `Option.get` and `Array.head`, all of which carry
a message. What remains with a null message, on the code reachable from these leaves:

- `java.util.ArrayDeque.removeFirst`, `pop`, `removeLast`, `getFirst`, `getLast` and its iterators in the Native
  javalib (`java/util/ArrayDeque.scala:371-376`, `:620-622`, `:412`, `:421`, `:725`, `:780`), and the same shape in
  `LinkedList`, `ConcurrentLinkedQueue` iterators (`ConcurrentLinkedQueue.scala:494`), `LinkedBlockingDeque` and
  `DelayQueue`.
- kyo-data's `Chunk.Indexed.head` (`Chunk.scala:570-573`) and `Chunk.last` (`:201-205`), and the `Span.sliding`
  iterator (`Span.scala:1151`).

On the two failing leaves the reachable calls of that list are: `CallbackRegistry.popTransient_<shape>()`, which is
`transientStack_<shape>.get().nn.pop()` (`CallbackRegistryShapes.scala:276-277` for `I_U`, `:306-307` for `II_I`)
and throws exactly this exception when the deque it gets is empty; `GuardCore.buffers.iterator()` guarded by
`hasNext` (`GuardCore.scala:181-183`, not reached by either failing leaf); `AssertScope` and `Finalizers`, which
only `poll` (`AssertScope.scala:93-100`, `Finalizers.scala:61`); and every `Chunk.head` in the kernel and core,
which sits under a size match or a non-empty check (`Kyo.scala:1300` onward, `TestRunner.scala:474-478`). I found
no unguarded call of any of these on the leaf pipeline (`Scope.run`, `Fiber.initUnscoped`, `Async.timeout`, the
heartbeat at `TestRunner.scala:320-334`, `AssertScope`), on the branch's added code (the diff of kyo-core,
kyo-kernel and kyo-prelude adds no `head`, `last`, `pop`, `removeFirst` or `dequeue` on a collection; its only
`removeLast` is the guarded one in `EffectTrace`), or in kyo-ffi's own runtime.

### 2.5 The candidates, ranked

1. `popTransient_<shape>()` on an empty deque. It is the only message-less `NoSuchElementException` site executed
   by both failing leaves, it sits in a `finally`, so it replaces any exception thrown by the call block, and it
   throws from kyo-ffi code that is identical on main. For it to fire, the deque returned by
   `transientStack_<shape>.get()` at the pop must not be the one pushed onto at the push. The generated code emits
   exactly one pop per push (`NativeEmitter.scala:278-280`, `:540`, `:600`, `:432-449`) and a failure between the push line and the
   `try` leaves an extra element, never a missing one, so a count mismatch is excluded. The Native `ThreadLocal`
   (`java/lang/ThreadLocal.scala:368-383`) returns a fresh `initialValue()` on every `get` only for a thread built
   with `Characteristics.NoThreadLocal` (`:372`, `java/lang/Thread.scala:72-74`, `:93-95`), and kyo's pool threads
   are built with the five-argument constructor, which sets `NoInheritThreadLocal` only (`Thread.scala:108-121`);
   the table is keyed by a `WeakReference` to the `ThreadLocal` and drops an entry whose referent reads as
   collected during `cleanUp` and `rehash` (`ThreadLocal.scala:141-168`, `:175-213`), but the transient stacks are
   fields of the `CallbackRegistry` module, which is a root. So this candidate needs a Scala Native runtime fault
   (a weak reference to a live module field reading null, or `Thread.currentThread()` changing identity inside one
   method) that I cannot demonstrate by reading. It stays first because nothing else on these leaves has the
   observed shape.
2. On the comparator leaf only: an exception thrown by `printStackTrace` inside the trampoline's `catch`. It
   escapes into C (section 4), unwinds on Linux into the generated `finally`, and if candidate 1 also fires there
   the pop's `NoSuchElementException` replaces it. This chain explains the Linux failure of that leaf only if the
   deque is empty at the pop, which again is candidate 1; on its own, an exception from `printStackTrace` would
   reach the leaf with its own class, and section 2.2 found none of that class in the symbolization code.
3. A message-less throw from the Native javalib somewhere on the leaf pipeline that only ffi-it triggers by timing.
   I found no such site; it is listed because the search was static.

## 3. Branch against main

`EffectTrace.scala` does not exist on `origin/main` (`git show origin/main:kyo-kernel/shared/src/main/scala/kyo/kernel/internal/EffectTrace.scala`
fails; main's `internal/` holds `CanLift`, `Context`, `KyoInternal`, `LiftMacro`, `Safepoint`, `Trace`,
`package`). On the branch it is attached at every handler catch site (`Handler.scala:98`, `:120`, `:149`, `:207`,
`:232`, `:279`, `:496`, `:575`) and spliced when a failure leaves the evaluator (`Eval.scala:456`, `:479-480`,
`:510-511`). That is branch-only, but it is not a mechanism for this failure: every one of those calls is total by
construction (section 2.1), and the one observable effect, forcing the throwable's stack trace to materialize on
the failing thread, is something main's kernel also did, unguarded, in `Trace.enrich`
(`origin/main:kyo-kernel/shared/src/main/scala/kyo/kernel/internal/Trace.scala:190-200`, reached through
`Safepoint.enrich` from `ArrowEffect.scala:594`, `:604`, `:616` and `Effect.scala:50`, `:59` on main). So
materialization under a C frame is not new to the branch either.

What is new on the branch and sits on the leaf's path is the rest of the kernel and core line: the evaluator and
its per-thread `Stack` pool (`Stack.scala:333-359`), `Safepoint` with its per-thread slot and its `ThreadLocal`
cache (`kyo-kernel/jvm-native/src/main/scala/kyo/kernel/internal/Safepoint.scala:82`, `:159`), the rewritten
`IOTask`, `Fiber`, `Scope`, `Async.timeout` and `Sync` (the diff lists `kyo-core/shared/src/main/scala/kyo/IOTask.scala`
+550, `Scope.scala` +270, `Fiber.scala` +265, `Async.scala` +77, `Sync.scala` +86, plus
`IOTaskPlatformSpecific.scala` on native). kyo-ffi, kyo-test and kyo-scheduler are identical to main, and the
kyo-data changes are additive (`Chunk.updated`, `Span.updated`, `Frame.callSite`, `IsFatal`, `bug.exception`).
The failure therefore comes from the branch's scheduling and evaluation of the same ffi code, not from a change to
that code, and the reading above narrows the surface to per-thread state of the pool thread the leaf runs on: the
transient stacks are the only per-thread state the two failing leaves touch, and they are read through
`ThreadLocal.get` on a thread whose `ThreadLocal` table the branch now also mutates through `Stack.pool`,
`Safepoint.local` and `IOTask.current`, each of which triggers the table's `cleanUp` and `rehash` on a miss or a
`set` (`ThreadLocal.scala:235-236`, `:282`, `:316`). Between one leaf's push and pop no kyo code runs, so a rehash
cannot sit between them; this is stated so the run in section 7 can confirm it rather than assume it.

## 4. The abort on macOS

Scala Native's exceptions are C++ exceptions (`runtime/Throwable.scala:16-25`, the `_UnwindException` wrapper). A
throw that is not caught before it reaches a C frame is delivered by `_Unwind_RaiseException`, whose first phase
steps every frame looking for a handler with the same libunwind stepping that `currentRawStackTrace` uses. The
trace observed locally stops at `_isort` after eight frames, which means `unw_step` cannot pass that frame of the
system libc's `qsort` on macOS arm64. An exception leaving the trampoline therefore cannot reach the handlers above
`qsort` (the generated `finally`, kyo-test's `Abort.run`), phase one returns end-of-stack, and the C++ runtime's
`__cxa_throw` calls `std::terminate`, which calls `abort`: that is the SIGABRT. On Linux the same C frames carry
`.eh_frame` (gcc emits it for all code on x86-64 and aarch64, and the test library is built with `cc -shared -fPIC
-O2`, CI log line 2287), so the exception unwinds through `qsort` into Scala code and the process survives, which
is why the same defect shows as a failed leaf on Linux and as an abort on macOS.

So the question is what leaves the trampoline. Two exits exist by construction: `peekTransient_<shape>()` outside
the `try` (`CallbackRegistryShapes.scala:310`), which throws `IllegalStateException` on an empty per-thread stack,
and `reportCallbackFailed` inside the `catch` (`:313-314`), which is not itself guarded, so anything thrown by
`println` or by `printStackTrace` escapes. In the comparator leaf `System.err` has been replaced by a
`PrintStream` over a byte array (`ItCallbackExceptionTest.scala:24-36`), so the `println` is not the risk; the
symbolization is, and section 2.2 found nothing in it that throws for a C frame, which leaves the empty stack at
`peek` as the escape whose downstream shape matches CI: on Linux it unwinds into the generated `finally`, whose pop
on that same empty stack throws the message-less `NoSuchElementException` that replaces it.

The reported local A/B (trace printing removed: both pass; frames resolved one by one first: both pass) does not
separate these. `printStackTrace` on Native is `getStackTrace` plus printing (`Throwables.scala:109-150`), and
`getStackTrace` caches the materialized array in the throwable (`runtime/Throwable.scala:67-74`), so resolving the
frames first and then printing runs exactly the same symbolization once; if that symbolization aborted, the
one-by-one variant would abort too. `EffectTrace.physical` (`EffectTrace.scala:37`) plays no part: it is a cache on
the suppressed carrier, filled only by `splice`, which never runs on the callback path. Given that CI fails a
different leaf in three of four runs and moves with timing, the local passes after each edit are most simply read
as the nondeterminism, not as the edits' effect. A run that prints the escaping exception's class from inside the
trampoline before anything else settles it (section 7).

## 5. The fix

Of the three options in the brief:

(a) making `EffectTrace.splice` total: it already is (section 2.1); there is nothing to change and changing it
would not touch this failure.

(b) not splicing when the throw site is inside a foreign frame: `splice` never runs on the callback path, and where
it runs it cannot throw; this is a change with no effect on the defect.

(c) the reporter carrying the exception out to the caller: on Native an exception must not cross the C frames at
all, since the runtime cannot unwind them on macOS (section 4); carrying the failure out can only mean recording it
as a value (on the `TaggedCallback`, or in the registry) and raising it after the downcall returns, which is a
contract change for kyo-ffi (today the contract is log, then return the zero default, `ItCallbackExceptionTest.scala:10-16`)
and does not by itself remove the abort, because the report would still be produced inside the frame.

The fix I would make has two parts, and only the second is the root cause.

First, the kyo-ffi trampolines have to honor their own contract that no exception reaches C, which they do not
today; this is a correctness defect independent of the branch and it is what turns any failure into an abort on
macOS. In `project/CallbackShapesGen.scala:349-357` move the `peekTransient_<shape>()` call inside the `try` so an
empty stack is reported through the same reporter and answered with the zero default, and in
`kyo-ffi/shared/src/main/scala/kyo/ffi/internal/FfiGenErrors.scala:19-22` make `reportCallbackFailed` total: wrap
the diagnostic and the `printStackTrace` in a catch-all that, on a secondary failure, prints one line naming the
original throwable's class and message and the secondary throwable's class, without touching the trace again. The
retained trampolines (`RetainedTrampolines_<shape>.scala:11-24`) already keep the lookup and the guard bookkeeping
outside the reported region and need the same treatment for the reporter only. This is not a workaround: the
contract is that the callback boundary is total, and the code is not.

Second, the `NoSuchElementException` itself, which this analysis narrows to the transient pop and cannot close
statically. The runner hides its origin: `TestRunner.scala:523` and `:531` keep only `t.toString`, and
`ConsoleReporter.scala:110-120` prints that diagram. The next step is a Native run of `kyo-ffi-it` with the
unexpected exception's stack trace printed, either by a reporter option that prints `getStackTrace` for a
non-assertion failure or by a temporary print at `resultToTestResult`, plus a print of the class of whatever
escapes the trampoline, and a print of `System.identityHashCode` of the deque at push and at pop in the generated
`kyoItSortInts` and `kyo_it_struct_read_handle` bodies. With the pop confirmed as the thrower and the two deques
shown to differ, the defect is in the Native `ThreadLocal` or its weak keys under the branch's thread usage, which
is a Scala Native issue to report with the reproduction below and to work around in kyo-ffi by keying the transient
stacks on the `Thread` object in a concurrent map rather than on `ThreadLocal`; with the deques shown equal, the
exception is not the pop and the trace names its real site. Rewriting the reporter alone would hide the
`NoSuchElementException` behind the new diagnostic line and leave that run to do later, so both parts belong to the
same change.

## 6. A kyo-free reproduction

Two programs, both Scala Native 0.5.12 with multithreading on, linked with a C file compiled by the same `cc
-shared -fPIC -O2` line CI uses.

The first tests whether Scala Native itself survives a trace printed inside a C callback frame, and whether an
exception escaping the callback aborts; it is the program the brief asks for:

```c
/* cb.c */
#include <stdlib.h>
#include <stdint.h>
```

Mode 0 and 1 answer whether printing a trace captured under `qsort` is safe on macOS arm64 and on Linux, on a thread
built the way kyo's pool builds its threads; mode 2 shows the abort on macOS and the propagation on Linux, which is
the section 4 mechanism with no kyo involved. If mode 0 aborts where mode 1 does not, the fault is Scala Native's
and belongs upstream with this program; if both pass, the abort seen locally came from an exception escaping the
trampoline, which is kyo-ffi's.

The second tests the transient stack mechanism in isolation, which is what the three `ItStructPtrTest` failures
point at: a `ThreadLocal[java.util.ArrayDeque[AnyRef]]` with an `initialValue`, pushed before and popped after a
downcall to a C function that does nothing, on a pool of threads built with `new Thread(null, r, name, 0L, false)`,
while other `ThreadLocal`s on the same threads are set and read between calls (to drive the table's `cleanUp` and
`rehash`), and with allocation pressure between the push and the pop so the collector runs. It passes if every pop
finds its element; a `NoSuchElementException` there is a Scala Native `ThreadLocal` defect, reproduced without kyo.
If it passes under every combination, the pop is not the thrower and the run in section 7 is the only way forward.
