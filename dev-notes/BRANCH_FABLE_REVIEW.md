# Held-Out Review: Is `kyo-compat-external-bindings` Causing Its Own CI Instability?

Reviewer: held-out Fable, analysis only. Range reviewed: `2e9bb02d40..d9a239210f` (160 commits, 136 files, +4990/-2086). Method: full log walk; deep reads of every production-behavior, test-behavior, and CI-infrastructure change; provenance checks of each flaky test against the base commit `2e9bb02d40` (= `origin/main`); failure views of the two visible failed full-matrix runs (`scripts/ci-logs.sh run 30967798105 / 30976807671`); the committed native-crash experiment register.

## Verdict

**(c) A mix, dominated by pre-existing latent flakes. Best estimate: ~75-80% pre-existing / environmental, ~20-25% self-inflicted.** The maintainer's hypothesis, that the branch's own changes are the primary source of the instability, is **not supported** by the evidence. The single biggest contributor to CI difficulty is the pre-existing flake density of the test estate (plus a pre-existing scala-native runtime crash) being run repeatedly through a 3-consecutive-green full-matrix gate that main never has to pass.

Grounding for the pre-existing side, checked commit-by-commit against the base:

- Every named intermittent failure I could trace resolves to code present at `2e9bb02d40`:
  - `WorkflowSchemaTest` racy pump predicate (`isTerminal || s == Running`): **present at base** (verified in the base file, line 269). Fixed by `ff86a060fc`.
  - `SqlClientPoolSlotLeakTest` "interrupted mid-statement" leaf with the incomplete fake handshake (no ParameterStatus): **present at base** (leaf at base line 211, `pgAuthOkBytes` unchanged until `d9a239210f`). Fixed by `d9a239210f`.
  - The `Async.timeout` fork-before-arm race: **present at base** (base `Async.scala` forks the body before `clock.unsafe.sleep(after)` is enqueued). This latent kyo-core bug is what hung `SqlConnectionCancelTest` for 2m. Fixed by `af3016ebb5` with a deterministic time-control regression test.
  - `SignalTest` combineLatestAll wakeup: base test synced on a nondeterministic ghost-waiter count. Fixed by `42b214ecb1`.
  - `ZIOsTest` interrupt-orphan race: test **present at base**; the branch made **zero commits to kyo-zio main sources** in the range, so the race in `ZIOs.run` is pre-existing.
  - `JsonRpcHandlerProgressPolicyTest` monotonic-progress hang: root-caused to a kyo-core `Sync.ensure` finalizer skipped on Abort short-circuit (Meter permit leak); the branch does not touch `Sync.ensure` or `Meter`.
  - kyo-aeron `TopicBackpressureReconnectTest` / `TopicInvariantsTest` / `TopicUniformInvariantsTest`: all present at base (kyo-aeron landed on main in `eae31e1d39`); the windows failure in run `30976807671` happened *before* the branch's aeron hardening commits.
  - The kyo-http streaming pool desync (`4fc29b5158`) states and I have no reason to doubt: "Pre-existing bug (client source was byte-identical to origin/main)". A real production bug, found because CI flaked, fixed with regression tests.
  - The native SIGSEGV: root-caused via an instrumented scala-native runtime to StackTrace `Context` InheritableThreadLocal aliasing (canary never trips; owner-tid aliasing on every crash; `inheritThreadLocals=false` gives 40/40 clean loops vs baseline crash-in-1-3). Nothing in the branch touches exception capture; the trigger is concurrency volume that base native tests also generate. (One caveat below in Open Questions.)
  - kyo-pod container failures: environmental at multiple levels, including two upstream runner regressions that arrived mid-campaign (runner image shipping podman 5.8.4 with the apt 4.9.3 conmon breakage, adopted fix `6081551098` = #1882; codeload 429s on the coursier action, `f1db832de3`), the Windows runner's Docker being in Windows-container mode (`00fabfe717`, 178 deterministic failures, correctly gated), missing cgroup delegation on arm64 rootless (`54c2a0313b`), and a podman docker-compat bug mistranslating `PidsLimit: 0` into `pids.max=1` (`23f6a5e551`).
- The two failed full-matrix runs visible to me failed on kyo-pod `ContainerItTest` (windows, environment) and kyo-aeron `TopicBackpressureReconnectTest` (pre-existing test) — not on anything the branch's production changes touch.

Grounding for the self-inflicted ~20-25%:

- Several of the intermittent failures that consumed CI attempts were in **tests the branch itself added** during the kyo-sql custody arc, which were initially racy: the reclaim-pool gate handshake deadlock in the branch's own new test (fixed `715c3a2ab7`), the handover-interrupt race (`7c109718f7`), the lease-fiber await (`f0d0679375`), the cancel-reclaim determinism pass (`7ba7149365`). These were found and fixed in-range, but they cost full-matrix attempts.
- The branch added new timing-sensitive machinery late (connection-pool reaper + a global 2s idle timeout for every test fork; forked-fiber response delivery in jsonrpc) whose full-matrix behavior is **not yet observed**: the last visible matrix runs predate them. This is untested risk, not observed damage (details in findings R1, R2).
- The CI-level crash-retry machinery deliberately tolerates two diagnosed crash classes, which reduces failure signal (finding R3).

Why 3-green is hard even without branch-caused regressions: with dozens of independent low-probability flakes across a matrix of this size, three consecutive fully green runs require the *product* of per-run green probabilities; a per-run flake rate as low as ~10% (a handful of 1-2% flakes across legs) gives only ~73% chance of 3 straight greens. Main appears stable partly because nobody demands 3 consecutive full-matrix greens of it and its per-push signal tolerates a retry. The branch's campaign is doing the flake-burn-down main never did; the burned-down flakes overwhelmingly turn out to be base bugs, which is itself evidence for the exonerating reading.

## Ranked Findings

**R1. New global test-fork timing machinery, matrix-unvalidated.** `93287ae816` + `31a07dc684` + `74bc10dddd` (should-fix / validate before the next matrix push).
The reaper design itself is sound: seq-gated publish read before the timestamp read (release's `lazySet` publish ordered before the volatile `sequences.get`), stale head claimed with the same head CAS `poll` uses (exactly-once vs poll/close), stop-at-first-fresh with the age-order approximation honestly documented after review (`74bc10dddd`), NonFatal-only per-connection close containment, no reaper for infinite-timeout pools, interrupted by `close()`. But two blast-radius consequences are new to every test fork in the repo:
  - `build.sbt` sets `-Dkyo.http.client.defaultIdleTimeout=2seconds` for **all** test forks (`kyo-settings`, not kyo-http's). Any test anywhere that uses the ambient default client and implicitly relies on connection reuse across a >2s idle gap (slow runner pauses included) will now silently reconnect; a test asserting reuse or connection counts would flake.
  - One background fiber waking every 1s now runs in every fork that touches the default client.
Neither has been through a full matrix run (the reaper landed Aug 17; the last visible matrix runs are earlier). Also see Open Question 2 on the clock context captured by `startReaper`.

**R2. jsonrpc response delivery is now asynchronous.** `d35569bddc` (nit, watch).
Replacing the silently-dropping `writerChannel.unsafe.offer` with a backpressuring `put` is the right fix (repro-first test: 35/100 dropped on the old path, 100/100 delivered on the new). But `enqueueResponse` forks an unscoped fiber per response, so response enqueue order relative to other outbound traffic is no longer the callback execution order. JSON-RPC does not mandate cross-message ordering, but any test (or client) asserting a strict wire sequence acquires a race that did not exist before. No observed failure attributes to this; it is a latent flake source to keep in mind.

**R3. CI crash-retry tolerates two diagnosed crash classes, reducing signal.** `6543956d39`, `06eb2f4482`, plus the pre-existing errno-104 retry (should-fix eventually, acceptable now).
`check_log` now retries a native binary that exits on SIGABRT/SIGBUS/SIGSEGV (134/135/139) *after* a fully-passing suite, and the retry re-runs only unrecorded tests via `testKyo --quick`. Scoped carefully: only fires with zero `*** FAILED ***`, OOM (137) is excluded, and the new mid-run-death scan makes the runner **stricter** than before (a link/optimize marker after the last `Tests:` line now fails on both the watchdog and self-exit paths, where the old code tolerated it on self-exit). Still: this permanently converts an intermittent teardown crash of the named shape into a green run. The commit itself names the crash "the known kyo-core finalizer-on-interrupt issue"; that core bug is being retried around at CI level rather than fixed (see T2 below, same root class). When the scala-native NoInherit fix is upstreamed and the finalizer issue fixed, these retries should be re-tightened.

**R4. The kyo-sql custody arc is the branch's largest new-concurrency surface.** `c24f3af0ec`..`cf48e7d5b8` (9 production commits: custody Local, orphan finalizer, claim/take handover, close-thunk custody, cancel-sidecar guards) (cleared with residual risk).
This is real machinery with real interleaving space, and its own new tests produced several of the campaign's intermittent failures before being made deterministic (all fixed in-range; see verdict). The production fd-leak it fixes (io_uring processSharedTransport, caught by kyo-test's end-of-run leak check, which itself **pre-exists at base**, e.g. base commits `e84a11f638`, `7fad91251c`) was a pre-existing bug. I read the custody additions in `SqlConnectionPool.scala` and found no red flag, but a static read cannot certify a handover protocol of this size; the container conformance suites are the real check and the tasks record them as run. Residual risk acknowledged, no finding.

**R5. Committed diagnosis artifacts and a leftover diagnostic workflow.** (hygiene, must not reach the PR)
Tracked at HEAD: `NATIVE_CRASH_BACKTRACE.txt`, `NATIVE_CRASH_BACKTRACE_4992.txt`, `NATIVE_CRASH_EXPERIMENTS.md`, `NATIVE_HEAP_CORRUPTION_DIAGNOSIS.md`, `SCALA_NATIVE_ISSUE_DRAFT.md`, `SINGLELINK_AB_DIAGNOSIS.md` at the repo root. Untracked: ~10 analysis .md files plus `.github/workflows/podman-diag.yml`. Ship-prep must strip all of these (`docs/design/numeric-scalar-dos-limits.md` is the one that belongs in-tree).

**R6. `dfad6b1abe` inheritThreadLocals=false: sound, and a (small) semantic change on the JVM too.** (cleared, note)
The causal evidence is as strong as this class of bug allows: instrumented runtime, canary-refuted external-clobber hypothesis, owner-tid aliasing on every crash, 0 crashes in 40 loops with the change, baseline crash in 1-3. The JVM-side effect is that scheduler threads no longer inherit InheritableThreadLocals from whichever thread happened to create them; that inheritance was nondeterministic (workers are created lazily by a busy parent worker), so code depending on it was already broken by design. JVM suites validated green. This is a workaround for an upstream scala-native bug; the register records the upstream report as the user's follow-up. Keep that follow-up alive: the workaround makes kyo immune, not scala-native fixed.

## Open Questions (need an empirical run to settle)

1. **Base-reproduction of the native SIGSEGV.** The experiment register's baseline (E0) was the branch, not `2e9bb02d40`. A short loop of `kyo-coreNative/test` at the base commit (crashes expected within ~3 loops) would close the last gap in "pre-existing" conclusively. Everything known about the mechanism (scala-native runtime ThreadLocal aliasing) predicts it reproduces.
2. **Reaper clock context.** `startReaper` runs `Clock.repeatWithDelay` under `Sync.Unsafe.evalOrThrow` at pool-init time. Confirm the reaper always binds the live clock regardless of which fiber first touches the lazily-initialized default client; a pool initialized inside a `Clock.withTimeControl` scope capturing the controlled clock would stall (or distort) reaping for the process lifetime.
3. **2s-idle blast radius.** Grep/run for tests using the ambient default client that assume connection reuse across a >2s gap; run one full matrix with the reaper + flag in place before counting any green toward the gate (the current HEAD's newest machinery has zero matrix runs behind it).
4. **Yaml native mismatch (#46).** Re-check whether the `YamlEventReaderTest` linux-x64 Native value mismatch still occurs on a HEAD that includes `dfad6b1abe`: if it was the same native memory-corruption class, NoInherit may have cured it; if it persists, it is a distinct native codec bug and is currently the only known unfixed intermittent failure on the branch.
5. **The two masked bugs (T1, T2).** Fix the kyo-core `Sync.ensure`-on-Abort finalizer leak and re-enable the jsonrpc monotonic test; close the `ZIOs.run` interrupt window and re-enable the orphan test. Both ignores are load-bearing only until those fixes exist.
6. **Recent-run visibility.** `gh run list` shows no branch runs after the two failures + four cancellations analyzed here, and the remote is ~40 commits behind local HEAD; the "each attempt a different failure" runs referenced by the latest commit messages (windows-JVM WorkflowSchemaTest, linux-x64-JVM SqlClientPoolSlotLeakTest, linux-x64-Native Yaml) were not directly inspectable. Their named failures are all accounted for above (two fixed in-range, one open as #46), which is consistent with the verdict, but I could not read those runs' full failure views myself.
